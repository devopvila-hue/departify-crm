## 1. Architecture (current state)

### 1.1 Topology

```
+-----------------------------+      +-----------------------------+
|         Railway / Docker    |      |        Supabase Postgres   |
|  apps/api  +  apps/web      |  --> |  one DB, multi-tenant       |
|  (one container, Fastify)   |      |  schema: 17 tables + 17     |
```

- **Same-origin**: API serves the built SPA from `apps/web/dist/` at root, `/api/v1/...` for REST, `/mcp` for MCP, `/openapi.json` + `/docs` for API discovery.
- **One container, one process** (no worker sidecar today — sequence worker is `runWorker()` launched from `apps/api/src/index.ts` in-process; the docstring in `apps/api/src/email/worker.ts` already flags "real deploy with multiple replicas you'd run it as a separate service via `pnpm worker`").

### 1.2 Backend composition root (`apps/api/src/server.ts`)

`buildApp()` registers, in order:

3. `rateLimit` (env-tunable default 300/min, auth 10/min).
4. `tenantPlugin` — global preHandler that calls `attachTenant(req)` on every request.
5. `setErrorHandler(sendError)` — every error returns the `ApiError` contract with `correlationId`.
6. `/openapi.json` + `/docs` (Swagger UI).
7. `/health` (in `health/routes.ts`).
8. `/api/v1/auth` (signup, login, logout, me, onboard-external).
9. `/api/v1/{contacts, companies, pipelines, deals, tags, notes, tasks, custom-fields, attention, search, service-keys}`.
10. `/api/v1/{email-senders, email-templates, sequences, suppressions}` (Sprint 5).

## 4. Tenancy model

`apps/api/src/tenants/plugin.ts` is the single source of truth. Behaviour:

1. **API key path first.** `Authorization: Bearer <token>` → SHA-256 lookup in `api_keys` (must be `active`, not revoked, not expired). Attaches `req.tenant = { actorKind: 'service', role: null, organizationId, userId: null, correlationId, db }`. Service actors bypass `requireRole` (the contract is the API key's `scopes`, not a user role).
2. **Session path.** Cookie `sid` or `Authorization: Session <token>` → SHA-256 lookup in `sessions`, join `users` + `memberships` (must match the session's org). Attaches `req.tenant = { actorKind: 'user', role, organizationId, userId, correlationId, db }`.
3. **Open routes.** No auth → `req.tenant` stays undefined; route handlers decide (e.g. `/api/v1/auth/signup` and `/health` don't require it).
4. **Tenant-scoped DB.** `attachTenant` calls `createDb(config.DATABASE_URL)` per request. Every business route filters by `eq(table.organizationId, tenant.organizationId)`. The `tenants/plugin.ts` source code says: *"There is no path through the codebase that bypasses this."*

Two helpers:
- `requireAuth` — global 401 if `req.tenant` is undefined.
- `requireRole(minRole)` — order owner=3, admin=2, member=1; bypassed for service actors.

Per-request DB instance is intentional (drizzle's `pgTable`s are stateless) — but this means no pool sharing across requests. The MCP server explicitly shares one pool across sessions (`getSharedDb()` in `mcp/server.ts`) to avoid "too many clients" against Supabase.

## 5. Auth

- **Passwords**: argon2id (memory=64MB, time=3, parallelism=4). Never returned by API.
- **Session tokens**: 32 random bytes, base64url. Stored as SHA-256 in `sessions.token_hash`. Cookie name `sid`, `httpOnly`, `SameSite=strict` in prod (`lax` in dev), `secure` in prod, 7-day TTL, refreshed on `/auth/login`.
- **API keys**: 40 random bytes, base64url. Stored as SHA-256 in `api_keys.token_hash`. Plaintext shown only at creation. `prefix` for human identification in logs. Scopes (jsonb array) per key.
- **Email provider credentials**: AES-256-GCM envelope with a key derived from `ENCRYPTION_KEY`. Stored as base64 in `email_senders.credentials_encrypted`. Decrypted **only inside the provider adapter**, never in route handlers, never logged, never returned to the client.
- **Webhooks**: HMAC-verified via the `rawBody` preserved by the custom content-type parser.

## 6. Permissions

- `membership_role` enum = `owner | admin | member`.
- `requireRole('member')` is the **minimum** for write operations on most modules (create deal, update deal, etc.).
- `requireRole('admin')` is required for **delete** on deals (see `apps/api/src/modules/deals/routes.ts` DELETE handler).
- **Service actors bypass role checks** but are constrained by `api_keys.scopes` (array of strings; per-scope enforcement is Phase 8 in `docs/departify-integration.md`).
- **Plan**: design ready for `resource × action × role × workspace × module` evolution. No ABAC engine yet; minimum robust model in place.

## 11. Risks (technical / product / migration)

### 11.1 Technical
- **Single-process sequence worker.** The `FOR UPDATE SKIP LOCKED` design is correct, but if the API process is restarted on every deploy (Railway default), in-flight enrollments are delayed. The comment in `worker.ts` already flags "real deploy with multiple replicas you'd run it as a separate service via `pnpm worker`" — this is a **Stage B hardening item**, not a Stage A audit fix.
- **`apps/api/src/tenants/plugin.ts` re-creates a drizzle instance per request.** Acceptable for low-mid scale; Supabase's connection pooler should be used before scaling beyond a few RPS per instance.
- **Custom fields live in `custom_values jsonb`.** No per-type constraints at the DB layer; all validation lives in route Zod schemas. If a new custom type is added without updating the route schema, the value lands raw.
- **No `request.id` is propagated to MCP responses.** The CRM HTTP routes get `correlationId`; MCP tool responses don't.
- **No rate limit per API key** — only per IP (`rate-limit` defaults). DEPARTIFY's batch jobs could be limited by IP-shared limits.

### 11.2 Product
- **Tenancy UX is invisible to the user.** No workspace switcher; `/auth/me` returns the first active membership. Multi-org users can't switch in-app yet.
- **No command palette** yet. The brief specifies one with create-record actions; Stage B must add it but stay minimal.
- **Departments are not yet real.** The `McpServer` already exposes a per-org tool surface that could be packaged as Department manifests, but no UI/UX exists.

### 11.3 Migration
- **All existing migrations are forward-only additive** (3 enums + 15+ tables + indexes). No `down` migrations. Rollback must be a forward fix.
- **Adding "Record" / "Relationship" custom field types** will require a new migration (junction table + per-tenant constraints).
- **`external_id` on `organizations` is already there** — DEPARTIFY mapping is ready.

## 13. Boundaries (Departify ↔ CRM ↔ OpenClaw)

| Concern | Departify (BOS) | CRM | OpenClaw (Execution) |
|---|---|---|---|
| Auth (humans) | DEPARTIFY identity | CRM cookie session (argon2id + SHA-256) | uses CRM cookie when calling CRM on behalf of a user |
| Auth (service) | DEPARTIFY service key → CRM via `external_id` mapping | CRM API key (Bearer) + `scopes` | uses CRM API key directly |
| Knowledge / memory | lives in DEPARTIFY | not here | OpenClaw memory tools |
| Workflows engine | DEPARTIFY orchestrates | CRM sequence worker (Phase 5) for email only | OpenClaw runs tasks scheduled by either side |
| Data ownership | DEPARTIFY keeps a mirror pointer (`external_id`) only | CRM is **the** system of record for contacts/companies/deals/notes/tasks/activities | does not store CRM data; reads/writes through CRM API |
| AI / LLM | DEPARTIFY runs AI for the user (Ask Departify) | CRM is **deterministic**; the `llm`/`ai` modules are a thin Anthropic proxy kept for backwards compat | OpenClaw drives AI for autonomous agents (different model policy) |
| Email send | DEPARTIFY may queue; CRM owns send timing + suppression + unsubscribe + bounce via `fake/resend/brevo` | sequence worker | OpenClaw can trigger CRM `POST /api/v1/email-senders` / `POST /api/v1/sequences/:id/enroll` |
| Audit | DEPARTIFY logs its decisions | CRM `audit_events` with `correlation_id` | OpenClaw logs its execution |

The **boundary contract** is:
- DEPARTIFY **drives** CRM via REST + MCP. It does not write to the same DB.
- OpenClaw **executes** via REST + MCP. It does not write to the same DB.
- CRM **owns** the data and the canonical writes. Both sides call in.
